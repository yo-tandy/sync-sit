# Study Booking Core — one_time (PR 2 of session-booking milestone) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** families with an accepted contact request can book one-time sessions; tutors confirm or decline. `study-sessions` collection goes live with rules, indexes, transactional confirm that claims schedule slots via a restorable override ledger, auto-decline of overlapping pendings, and full notification fan-outs. Recurring inputs are REJECTED in this PR (invalid-argument 'Recurring booking is not yet available') — PR 3 wires them.

**Scaffold contract (authoritative — wire, don't fork; amend consciously where listed):** apps/study-functions/src/types/session.ts (SessionDoc → `study-sessions/{sessionId}`), types/status.ts (SessionStatus pending|confirmed|declined|cancelled|modified|completed — 'modified' is NEVER written in v1; assert-unreachable), validation/session.ts (bookSessionInputSchema — restrict to type:'one_time' for this PR via a superRefine rejecting 'recurring').
**SessionDoc additions (amend the scaffold type):** `studentIds: string[]` + denormalized `students: {firstName: string, age: number}[]`; denormalized `familyName`, `parentName`, `tutorName` (parents can't read tutor docs and vice versa — StudyContactRequestDoc precedent); `reminderSent?: boolean`; `completedAt?`; `cancellationReason?`; `cancelledFromStatus?`; `contactRequestId?` (provenance).

**Templates to READ first:** the milestone design docs (memory + this plan); apps/study-functions/src/availability/getTutorAvailability.ts (gate chain + data loads + ParisNow usage — PR 1); apps/study-functions/src/contact/{sendTutorContactRequest,respondToTutorContactRequest}.ts (gates, transaction, notifyAllParents fan-outs); apps/functions/src/appointments/ (sit's confirm/cancel override handling — note its slot merge is LOSSY; ours must not be); packages/study-core/src/utils/availability.ts (computeDayAvailability + ConfirmedBlock); tests/integration/study-sessions/get-tutor-availability.test.ts (emulator + seed idioms); firestore.rules studyContactRequests block (the rules template).

**Core invariants:** "pending is a proposal, confirm is the claim" — pending sessions never block availability and never write overrides; CONFIRM is the only claim point, inside one `db.runTransaction` (all reads before writes); override docs get `{appSource:'study', reason:'study_session', sessionBlocks:[{sessionId, startIdx, endIdx}]}` — restorable ledger, AND-merge with existing overrides, NEVER resurrect slots we didn't block, treat any override without sessionBlocks as opaque; rate is snapshotted server-side from the live offering at book time; 24h minimum notice enforced at book AND re-checked at confirm; callable-only writes (rules deny all client writes); every notification respects notifPrefs categories (book→tutor newRequest; confirm→parents confirmed; decline→parents cancelled).

## Task 3: respondToSession callable — the transactional claim (TDD)
- `apps/study-functions/src/sessions/respondToSession.ts`. Input {sessionId, action: 'confirm'|'decline'} (zod enum exactly these).
- Transaction: tx.get(session) → assert exists, status 'pending', tutorUserId===uid → decline: tx.update status 'declined' (no override) → confirm: tx.get(overrides/{date}) + tx.get(confirmed sessions same tutor+date via (tutorUserId,status,date)) → recompute availability for the padded block (computeDayAvailability with the CURRENT override + confirmed blocks) → free? tx.update session 'confirmed' + tx.set override merge: base slots = existing override slots ?? weekly-day slots; AND-in the padded block as false; append sessionBlocks entry {sessionId, startIdx, endIdx}; set appSource 'study', reason 'study_session' (preserve existing fields if the doc predates us — read-modify-write inside the tx) : else failed-precondition 'This time is no longer available'.
- Re-check the 24h notice at confirm (a pending request can go stale) — failed-precondition 'This request is too close to the session time'.
- POST-transaction: auto-decline overlapping pendings — query tutor's pending sessions same date, any whose padded block intersects → update status 'declined' + statusReason 'slot_taken' + notify each family (cancelled prefs). Then notify the requesting family (confirmed prefs on confirm / cancelled on decline). Audit both actions.
- Integration tests: confirm happy (session confirmed + override created with correct slots false + sessionBlocks entry + weekly grid outside the block preserved), decline (no override), double-respond race (Promise.all both confirms → exactly one wins, loser failed-precondition), conflicting confirm rejected after another session claimed the block, wrong tutor, unknown session, stale-notice rejection, auto-decline of overlapping pending (+ its notification + non-overlapping pending survives), coexisting override preserved (pre-seed a sit-style override doc with some slots false and NO sessionBlocks → confirm must AND-merge, keep those slots false, keep its fields).
- Availability integration (closes the loop): after confirm, getTutorAvailability shows the padded block false for the approved family.
- Commit: `feat(study-functions): transactional session confirm with restorable override claim`
