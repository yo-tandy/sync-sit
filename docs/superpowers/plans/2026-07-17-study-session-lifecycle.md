# Study Session Lifecycle (PR 4 of session-booking milestone) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** the full session lifecycle after confirm — cancellation (one_time, single instance, whole series) with lossless override-slot restoration, the hourly completion cron (including deferred parent-series completion), and the session-reminders cron. Feature stays dark until the UI PRs.

**Scope decisions (locked):** any-time cancellation, both parties, reason REQUIRED, other side notified, no enforcement window (late cancels get nothing special in v1). Auto-completion hourly. Reminders 23–25h window per the sit pattern. 'modified'/'rescheduled' still never written.

**Templates to READ first:** apps/functions/src/appointments/cancelAppointment.ts (role detection, cancelledFromStatus, notification tone); apps/functions/src/scheduled/sendReminders.ts + tests/integration/scheduled/send-reminders.test.ts (runX(db,now) pattern + window/dedup/pref test idioms); apps/study-functions/src/sessions/{sessionOverride.ts,generateInstances.ts,respondToSession.ts} (the ledger you must now RESTORE from); scheduled/extendRecurring.ts (per-doc tx isolation idiom); types/{session,sessionInstance,status}.ts.

**Core invariant — lossless restoration (the whole point of the ledger):** removing a claim = remove its sessionBlocks entry, recompute the override doc's slots as (base for that day = weekly grid — NOT holiday grid, matching how claims were merged) AND all remaining blocks' subtractions AND any slots that were false for FOREIGN reasons. Practical algorithm (document it in sessionOverride.ts): you cannot naively flip the removed block's slots true — a foreign override or an overlapping remaining block may also cover them. Correct approach: start from the override's CURRENT slots; for each slot in the removed block's padded range, set true ONLY IF (a) the weekly grid has it true AND (b) no REMAINING sessionBlocks entry covers it AND (c) the doc is study-owned for that slot… (c) is unknowable per-slot — so the SAFE rule: if the override doc has FOREIGN provenance (reason not 'study_session' OR it predates us with extra fields), never flip slots true, only remove the ledger entry (conservative: the slot stays blocked until the foreign owner clears it; comment this). If the doc is purely ours (reason 'study_session', appSource 'study'): recompute slots = weekly-day grid AND-blocked by all REMAINING entries; if no entries remain → DELETE the override doc. ## Task 1: cancelSession (one_time + series)
- `sessions/cancelSession.ts`: input {sessionId, reason: min 3 chars}. Caller = the session's tutor OR a parent of the session's family (role detection à la cancelAppointment; permission-denied otherwise). Valid from status pending|confirmed → 'cancelled' + statusReason 'cancelled_by_family'|'cancelled_by_tutor' + cancellationReason + cancelledFromStatus + cancelledAt. Pending cancel = status flip only (no overrides exist). Confirmed one_time cancel: transaction — restore the override per the invariant, flip the session. Confirmed RECURRING cancel (series): transaction per the confirm pattern — parent → cancelled; every instance with status 'scheduled' AND date >= today(Paris) → 'cancelled' + statusReason (same as parent) + restore each date's override; past/completed/conflict_skip instances untouched. ONE notification to the other side (series-level for recurring), cancelled prefs. Audit.
- Tests: cancel by family from pending (no override churn); by tutor from confirmed one_time (override slots restored EXACTLY to pre-claim state — assert the full 96-grid equality against a pre-captured snapshot; override doc deleted when ours-and-empty); series cancel (future instances cancelled, past instance untouched, every future override restored, ONE notification); FOREIGN-override conservation (cancel a claim merged into a pre-existing sit-style doc → ledger entry removed, foreign slots stay false, foreign fields preserved); reason required (invalid-argument); wrong party (permission-denied); double-cancel (failed-precondition); terminal statuses rejected.
