# Study Recurring Engine (PR 3 of session-booking milestone) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** weekly recurring sessions — booking, confirm-with-skips instance generation over an 8-week rolling window, the extendRecurring cron, and instance-aware availability. Feature stays dark until the UI PRs.

**Scaffold contract:** apps/study-functions/src/types/sessionInstance.ts is the instance shape (path `study-sessions/{sessionId}/instances/{instanceId}`) — wire it with these conscious amendments: **instanceId = the date string "YYYY-MM-DD"** (one instance per date per series — idempotency for extendRecurring, O(1) lookup from override blocks; update the scaffold comment), plus additive fields `reminderSent?: boolean`, `completedAt?`, `cancellationReason?`, `statusReason?: 'cancelled_by_family' | 'cancelled_by_tutor' | 'conflict_skip'`. types/session.ts: add `endDate?: string` (open-ended series when absent). validation/session.ts: REMOVE the Task-1 superRefine rejection of 'recurring'; reconcile the recurring input to `recurringSlot: {day: z.enum(DAYS_OF_WEEK from @ejm/shared-core), startTime}` semantics — the scaffold's `recurringDayOfWeek: number` is superseded (conscious amendment, comment it); doc stores canonical `recurringSlots: RecurringSlot[]` (v1: exactly 1 entry), `schoolWeeksOnly: boolean` (input default true), `endDate?`.

**Authority split (from the milestone design — comment it on the types):** parent SessionDoc.status governs the SERIES (pending→confirmed→cancelled|completed); InstanceStatus governs occurrences (scheduled|cancelled|rescheduled|completed — 'rescheduled' is in the vocabulary but NEVER written in v1). Parent 'confirmed' + instance 'cancelled' = series live, that date off. Instances exist ONLY for confirmed series — never for pending. Holiday-skipped dates get NO instance; conflict-skipped dates get an instance with status 'cancelled' + statusReason 'conflict_skip' (a visible gap, not a silent absence).

**Templates to READ first:** apps/study-functions/src/sessions/{bookSession,respondToSession}.ts + availability/computeDateAvailability.ts (PR 2 — the gate chain, the tx claim, the shared composition, the override-merge helper: REUSE its merge logic per-date, factor it if it's inline); packages/study-core/src/utils/availability.ts (expandRecurringDates — already shipped in PR 1 with holiday/DST tests); apps/functions/src/scheduled/sendReminders.ts (the runX(db, now) injectable cron pattern); tests/integration/study-sessions/* (idioms; seed tutor2 has the schedule).

**Core invariants:** confirm-with-skips (zero bookable dates → failed-precondition, parent stays pending); ONE transaction for the recurring confirm (reads: parent, per-date overrides, per-date confirmed one_time sessions, collectionGroup instances for the tutor in range — ALL before writes; writes: parent update + ≤8 instance creates + ≤8 override merges — far under limits); override sessionBlocks entries gain `instanceId` (amend the PR 2 block shape additively — one_time blocks simply have no instanceId); extendRecurring is idempotent (date-keyed instance IDs, create-if-absent) and self-healing (each run generates up to the full 8-week horizon); pending recurring requests never touch availability; holiday + schoolWeeksOnly semantics exactly as expandRecurringDates implements them (schoolWeeksOnly drops holiday dates entirely; schoolWeeksOnly=false attempts them against the tutor's holiday-adjusted grid → conflict_skip if unavailable).
